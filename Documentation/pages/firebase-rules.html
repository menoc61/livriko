Firebase Rules

Firebase security rules control who can read and write data in your Firestore database. Configuring proper rules is essential to protect user data and prevent unauthorized access.

Why Security Rules Matter

Firestore security rules act as a firewall for your database. Without proper rules, anyone could read or write to your Firestore collections, exposing sensitive user data. Livriko provides default rules that you can import directly into your project.

Security Warning

Never use overly permissive rules such as allow read, write: if true; in production. This exposes your Firestore data to unauthenticated access and poses a significant security risk. Always ensure rules require authentication where appropriate.

Default Firestore Rules

Navigate to Firestore Database → Rules in your Firebase console and paste the following rules:

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // Riders collection — users can only access their own data
    match /riders/{riderId} {
      allow read, write: if request.auth != null
        && request.auth.uid == riderId;
    }

    // Drivers collection — drivers can only access their own data
    match /drivers/{driverId} {
      allow read, write: if request.auth != null
        && request.auth.uid == driverId;
    }

    // Rides collection — authenticated users can read/write
    match /rides/{rideId} {
      allow read: if request.auth != null;
      allow write: if request.auth != null;
    }

    // Locations collection — real-time driver locations
    match /locations/{locationId} {
      allow read: if request.auth != null;
      allow write: if request.auth != null;
    }

    // Messages collection — chat between riders and drivers
    match /messages/{messageId} {
      allow read, write: if request.auth != null;
    }

    // Notifications collection — push notification payloads
    match /notifications/{notificationId} {
      allow read, write: if request.auth != null;
    }
  }
}

Rule Breakdown

Each collection has specific access patterns:

Collection Rule Pattern Description
riders Owner-only access Each rider can only read/write their own document (matched by UID)
drivers Owner-only access Each driver can only read/write their own document (matched by UID)
rides Authenticated read/write All authenticated users (riders, drivers, admin) can access ride data
locations Authenticated read/write Drivers write their location; riders read driver locations
messages Authenticated read/write Chat messages visible to both parties in a ride
notifications Authenticated read/write Notification payloads for FCM delivery

Deploying Rules

You can deploy rules using either the Firebase Console or the Firebase CLI:

Method 1: Firebase Console

Open the Rules Editor

Go to Firebase Console → Firestore Database → Rules tab.

Paste the Rules

Replace the existing rules with the Livriko rules provided above.

Publish

Click "Publish" to apply the rules. Changes take effect immediately.

Method 2: Firebase CLI

# Navigate to your project directory
cd your-project

# Deploy only Firestore rules
firebase deploy --only firestore:rules

# Or deploy rules from a specific file
firebase deploy --only firestore:rules --project your-project-id

Testing Rules with the Firebase Emulator

Before deploying to production, test your rules locally using the Firebase Emulator Suite:

# Install the Firebase CLI (if not already installed)
npm install -g firebase-tools

# Start the Firestore emulator
firebase emulators:start --only firestore

# In another terminal, run your tests
# The emulator will use rules from firestore.rules in your project

Common Rule Patterns

Here are some common rule patterns you may need:

// Allow only the admin SDK (server-side) to write
match /admin-data/{docId} {
  allow read, write: if request.auth != null
    && request.auth.token.admin == true;
}

// Allow write only if the document doesn't already exist
match /rides/{rideId} {
  allow create: if request.auth != null;
  allow update: if request.auth != null
    && request.auth.uid == resource.data.riderId;
}

// Allow read based on a subcollection relationship
match /rides/{rideId}/chat/{messageId} {
  allow read, write: if request.auth != null;
}

Debugging Rule Errors

If users encounter "Permission Denied" errors, check the following:

Error Common Cause Fix
Permission denied on read User is not authenticated or UID doesn't match Ensure the user is signed in and accessing only their own document
Permission denied on write Rule doesn't allow the write operation Check the rule conditions and ensure the user meets all requirements
Missing or insufficient permissions Rules are not deployed or stale Re-deploy rules and clear the browser cache
Admin SDK errors Service Account lacks Firestore permissions Check the Service Account role in Firebase Console → IAM
Tip

Use the Firebase Console's "Rules Playground" to test individual rules against mock authentication contexts and request data before deploying to production.
